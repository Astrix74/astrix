[《智能体 harness》系列](/zh/series/agent-harnesses/)是从构建者的角度看编程智能体的：智能体循环、工具、上下文窗口。这篇文章则从另一侧来看，也就是把任务交给智能体的开发者。这种交接中出的大多数问题，只要你知道智能体能看到什么、看不到什么，都是可以预料的，所以下面每一条习惯都附上了背后的原因。

这些是工作习惯，不是定律。智能体和它们的工具变化很快，所以请把本文当作 2026 年底的一份快照，并用你自己的实际结果来检验它。

## 任务开始前

**像对新队友那样，把需要的信息给它**。智能体每次会话开始时，除了它能读到的东西，对你的项目一无所知。大多数编程智能体会在一开始就把一个项目说明文件加载进上下文。比如 Claude Code 会在会话开始时把 `CLAUDE.md` 文件放进上下文（[《上下文工程》](/zh/writing/context-engineering/)）。这个文件用来写那些对每个任务都成立、又很难自己发现的东西：怎么构建和测试，从代码里看不出来的约定，哪些目录不要碰。让它保持简短。文件里的所有内容在每一步都会被重新发送，一个写满了很少用得上的规则的长文件，会和任务争夺模型的注意力。

**说清楚怎样才算完成**。“修复日期 bug”有很多种满足方式，其中有些是错的。“RSS 订阅源中的日期应采用 RFC 822 格式；添加一个修复前失败、修复后通过的测试”则是可以检验的。智能体靠行动并读取反馈来工作（[《智能体循环》](/zh/writing/what-a-harness-is/)），所以要给它一个它能自己运行的检查。一条能证明成功的命令，比一段描述成功的文字更有价值。

一份简短的任务说明就能覆盖大部分要点：

```text
Goal:        RSS feed dates are RFC 822, e.g. "Wed, 21 Oct 2026 00:00:00 GMT".
Where:       src/pages/rss.xml.ts; date helpers are in src/lib/posts.ts.
Done when:   `pnpm build` passes and dist/rss.xml has RFC 822 dates.
Constraints: no new dependencies; don't change the post URLs.
```

**任务的规模要能装进一个上下文**。如果一个任务需要智能体把整个子系统都装在脑子里，它就会被推向上下文窗口的极限，而在那里，它对内容的回忆会变差。把大的改动拆成若干步，每一步都有自己的检查。不相关的工作就开一个新会话，而不是让旧的对话记录被过时的输出填满。

## 任务进行中

**对任何不简单的任务，先要一份计划**。“Building effective agents”一文把**透明性**（transparency），即“明确展示智能体的规划步骤”，列为它的三条原则之一。读一份计划只要一分钟。读一份错误的 400 行 diff 要久得多，把它理清楚也一样。在计划阶段，你还能在被误解的需求变成代码之前就把它揪出来。

**让它自己跑检查，并看看它到底跑了什么**。相比聊天窗口，用智能体的意义就在于它能运行测试、读懂失败信息、然后再试一次。那就让它去做。但要读完整的对话记录，而不只是最后那条消息。“所有测试都通过了”只是一个说法，命令和它的输出才是证据。检查跑的是不是该跑的测试，并确认没有哪个测试是为了达到这个结果而被跳过或删掉的。

**尽早打断**。如果智能体走错了方向，当时就叫停，给它重新指路。它在错误方向上每多走一步，都会往上下文里多塞一些输出，而会话剩下的部分都得绕着这些输出工作。

**与其争论，不如重开**。当一个会话已经在原地打转时，上下文里塞满了失败的尝试和相互矛盾的错误信息。最快的解决办法往往是开一个新会话，配上一份更好的任务说明，写进你学到的东西：“X 里那个显而易见的修法行不通，因为 Y”。

## 任务完成后

**像审查同事的 pull request 一样审查 diff**。智能体可能会自信地犯错，而且错得看起来合情合理。下面这些常见的失败模式值得逐一排查：

- 改了测试去迁就代码，而不是反过来
- 把错误吞掉了，而不是处理它
- 新写的辅助函数与已有的某个函数重复
- 改动超出了任务所需的文件范围
- 为了标准库本来就能做的事引入了新依赖

**核实关于外部世界的说法**。智能体对库 API、版本和文档的了解有截止日期，而且即便在截止日期之前也可能出错。当一个改动依赖于某个外部 API 的行为时，去查当前的文档，或者让智能体去抓取文档，并引用它找到的内容。

**决定权留在你手里**。智能体可以找到 bug、写出修复、跑完测试。但这个改动对项目来说对不对，仍然由你来判断。推送、部署，以及任何会影响到其他人的事情，也都由你决定。

## 安全习惯

**定好哪些事它可以不经询问就做**。读文件和跑测试风险很低。删除文件、改写 git 历史、执行数据库迁移或通过网络发送任何东西，则不然。大多数编程智能体都允许你设置哪些命令需要批准。用好这个设置，放宽权限时要有意为之，而不是一路点“允许”，直到确认提示不再弹出。

**别让它碰到机密**。智能体读到的任何东西都可能进入它的上下文，再从那里进入日志、提交信息或 API 请求。不要把凭据粘贴到会话里，并优先采用智能体根本用不到凭据的环境配置。

**把抓取来的内容视为不可信的**。网页或文件里可能包含故意写得像指令的文字。一个构建良好的 harness 会把工具输出当作数据，而不是命令。确认你用的 harness 也是这样，并且在让智能体处理你无法掌控的内容时要格外小心。

> [!TIP] 要点
> - 像对新队友那样给智能体交代任务：东西在哪里，怎样才算完成，以及一条能证明完成的命令。
> - 让任务足够小，能装进一个干净的上下文；不相关的工作就开新会话。
> - 不简单的工作先要计划。尽早打断。与其争论，不如重开。
> - 看命令和输出，而不只是看总结。像审查同事的 diff 那样审查它的 diff。
> - 有意识地设置权限，把机密挡在外面，并把抓取来的内容当作数据。
